## Architecture

```text
TradingService ──► mutates (risk → reserve → match → CommandBatch WAL)
        │
       WAL  (Source of Truth)
        │
 live: AccountRegistry + per-instrument Engine/Book + shared ReservationStore
        │
 trading.ReadModel   ← thin snapshot API over the SAME objects (not a 2nd ledger)
        │
 QueryService        ← transport-independent, read-only views + AsOfSequence
        │
 gRPC QueryService adapter (query.proto)
```

### Invariant

> QueryService is a **projection/read boundary**, not another owner of financial truth.

| Component | Role |
|-----------|------|
| WAL | Authoritative history |
| AccountRegistry | Live `*domain.Account` + RWMutex for settle vs snapshot |
| ReservationStore | Live capacity claims (shared, internally mutexed) |
| InstrumentExecutor | Live book/orders/trades; `x.mu` single-writer |
| ReadModel | Pointers + snapshot methods only |
| QueryService | Builds immutable views; never mutates |

**Why both ReadModel and AccountRegistry?**  
- `AccountRegistry` = synchronized ownership of live account objects (trading settle + query snapshot).  
- `ReadModel` = query-facing façade bundling Accounts + Res + Router + EventSeq so `application/query` does not call Submit/Cancel or poke executors ad hoc.  
Neither is a separately written balance store.

## Consistency contract (CTO-clarified)

**Best-effort process-local snapshot with an observation sequence.**

```text
AsOfSequence = global EventSeq.Load() observation/watermark
               while constructing the response.

It is NOT a guarantee that every field represents exactly that sequence.
It is NOT MVCC / serializable isolation / multi-lock freeze.
```

Independent sync domains (no common transaction boundary):

| Domain | Lock |
|--------|------|
| Account cash/positions | `AccountRegistry` RLock (internally consistent pair) |
| Reservations | `ReservationStore` mutex |
| Orders/trades | `InstrumentExecutor.x.mu` |
| Sequence | `EventSeq` atomic |

**Honest residual:** `OpenOrders` count is a separate scan and may move vs the cash RLock snapshot under concurrent fills/cancels.

**Not claimed:** “point-in-time at sequence N” or “transactionally consistent GetAccount.”

## Concurrency

- Query does **not** take a global lock around all instruments for GetAccount cash.  
- Settle uses AccountRegistry **WLock**; snapshots use **RLock**.  
- Matching remains per-instrument `x.mu`.  
- P6.1-C1 still applies for concurrent multi-instrument **mutation** of the same account.  
- AccountRegistry makes settle + query race-clean for ledger fields.

## Known limitations

1. Not MVCC / SI — per-domain locks.  
2. Page tokens = index into **per-request** sorted snapshot (not durable cursors).  
3. No external read DB (by design).  
4. Auth still trusts `account_id` (same P6.1 boundary).  
5. Cold start: recover trading state (P5), then wire ReadModel — no separate query rebuild pipeline.  
6. OpenOrders count is best-effort vs cash snapshot under concurrency.

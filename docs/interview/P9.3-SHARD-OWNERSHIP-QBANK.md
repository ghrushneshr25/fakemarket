# P9.3 — Shard Ownership (CTO Q-bank)

> Tracked copy of the P9.3 interview bank (moved out of gitignored `.help/` at CTO request).
> Implementation: `f514a63`. Milestone: 🟢 ACCEPTED / CLOSED.

**Q1. Why explicit ownership after P9.1/P9.2?**  
Implicit “who holds the runner owns the shard” cannot fence stale executors after release/restart. P9.3 adds OwnerID + epoch + Validate before mutation.

**Q2. What is OwnerID vs WorkerID?**  
WorkerID = execution host index. OwnerID = control-plane identity (`worker-N`). Mapped 1:1 today; kept distinct for future distributed ownership.

**Q3. Ownership chain?**  
`InstrumentID → ShardID → OwnershipRegistry(OwnerID,Epoch) → WorkerID → runner → fence → Executor → WAL`.

**Q4. Ownership states?**  
`UNOWNED → ACQUIRING → OWNED → RELEASING → UNOWNED`.

**Q5. What is OwnershipToken?**  
`{Shard, Owner, Epoch}` — internal authorization context. Never client-controlled.

**Q6. Who is the ownership authority?**  
In-process `OwnershipRegistry` (Acquire/Release/Validate). Not clients, not transport.

**Q7. When does epoch bump?**  
On every successful first acquire (global monotonic). Same-owner re-acquire is idempotent (no bump).

**Q8. Why not wall-clock leases?**  
Non-deterministic under pause/GC; races. Epoch fencing is deterministic.

**Q9. Startup ownership?**  
Attach: EnsureShard all → Acquire per worker → set tokens → Start → Ready. No Ready without exclusive ownership.

**Q10. Shutdown ownership?**  
Stop admission → drain queues → ReleaseAllByOwner → clear tokens → WAL close.

**Q11. Where is fencing enforced?**  
(1) Before enqueue `validateShard`. (2) At exec time before `InstrumentExecutor.Submit/Cancel` (queued cmds cannot run after release).

**Q12. Central stale-owner test?**  
`TestP93_StaleOwner_ZeroFinancialMutation`: stale token → error; cash unchanged; WAL seq unchanged.

**Q13. Duplicate acquire?**  
Second owner → `ErrAlreadyOwned`. Concurrent same shard → exactly one winner (`TestP93_ConcurrentSameShard_OneOwner`).

**Q14. Release wrong owner/epoch?**  
`ErrNotOwner` / `ErrOwnershipEpochMismatch`.

**Q15. Is ownership a financial WAL event?**  
No. Control-plane only. Financial SoT remains shared WAL events.

**Q16. Does fencing change match semantics?**  
No. Fence fail = reject before mutation. Success path identical to P9.2.

**Q17. Shared-account under ownership?**  
Unchanged: ReservationStore + AccountRegistry concurrency; ownership is per-shard not per-account.

**Q18. Multi-worker + ownership?**  
Each worker holds tokens for its shards; Validate uses registry, not local belief alone.

**Q19. Metrics?**  
`ownership_acquire_total`, `ownership_release_total`, `ownership_fencing_rejections_total{reason}`.

**Q20. Out of scope?**  
Multi-process ownership, Raft/etcd, failover, live migration, remote RPC, client tokens, wall-clock TTL.

**Q21. Silent drops?**  
Forbidden. Fence failures are explicit errors (`ErrNotOwner`/`ErrStaleOwnership`).

**Q22. Idempotent re-acquire?**  
Same owner while OWNED returns current token; does not split-brain or bump epoch.

**Q23. Epoch go backward?**  
Never on successful acquire. Stale lower epoch always fails Validate.

**Q24. Bootstrap partial failure?**  
Acquire error aborts Attach; process not Ready.

**Q25. After shutdown OwnedCount?**  
0 (`TestP93_Shutdown_ReleasesOwnership`).

**Q26. ExecuteWithToken?**  
Test helper: Validate token then Submit — proves stale path without production client tokens.

**Q27. SetWorkerTokenForTest?**  
Test-only injection after forced release/reacquire to restore live path.

**Q28. NumWorkers=0?**  
Legacy direct executor path; no ownership registry required.

**Q29. Race?**  
`go test -race` green including concurrent acquire and multi-worker.

**Q30. Fuzz?**  
`FuzzP93_Ownership` acquire/release/validate.

**Q31. P8.6 conservation?**  
Ownership ops alone mutate no cash/positions. Fence rejects leave baseline intact.

**Q32. Durable-before-ack?**  
Unchanged; fencing is before mutation, so no ack without durable success on pass path.

**Q33. Split-brain in-process?**  
Prevented by registry mutex + single OWNED record per shard.

**Q34. Why ACQUIRING/RELEASING states?**  
Lifecycle clarity for future async ownership transfer; currently transitional under lock.

**Q35. Can two workers own same shard?**  
No. Acquire second → ErrAlreadyOwned.

**Q36. Instrument move between shards?**  
Out of scope (no live migration). Topology fixed at bootstrap.

**Q37. Recovery after crash?**  
WAL recovery rebuilds financial state; ownership re-acquired fresh at next Attach (new epochs).

**Q38. Stale token after re-acquire?**  
Old epoch fails Validate even if same OwnerID string.

**Q39. ADR?**  
0057 — Shard Ownership.

**Q40. Relation to ADR 0055/0056?**  
0055 placement; 0056 workers; 0057 explicit ownership/fencing on top.

**Q41. Hot path cost?**  
Validate = mutex + field compares; bench `BenchmarkP93_OwnershipValidate`.

**Q42. Queue full vs fence fail?**  
Queue full → backpressure error. Fence → not-owner/stale. Distinct.

**Q43. Cancel path fenced?**  
Yes; same validateShard before cancel exec.

**Q44. Global vs per-shard epoch?**  
Global monotonic counter assigned into per-shard record — simple total order of acquires.

**Q45. Why not store ownership in WAL?**  
Would mix control-plane with financial SoT; recovery semantics more complex; P9.3 keeps separation.

**Q46. Principle?**  
> Exactly one authoritative owner per shard while OWNED; every financial mutation is fenced by a current Owner+Epoch token; stale owners produce zero financial side effects.

**Q47. Failure mode if fence skipped?**  
Stale worker could match/reserve/append — split financial authority. Fence is mandatory.

**Q48. Evidence classes for CTO?**  
IMPLEMENTED (code), TESTED (P93_*), OBSERVED (make check/race/fuzz), INFERRED (future multi-process), NOT VERIFIED (distributed consensus).

**Q49. Next after P9.3?**  
P9.4+ replication / consensus / failover — ownership model designed to extend without rewrite.

**Q50. What P9.3 deliberately does NOT claim?**  
Multi-process HA, automatic failover, or 🟢 ACCEPTED without CTO sign-off.

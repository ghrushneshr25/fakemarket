# P10.4 — End-to-End Failure / Recovery Demo

## Status

**IMPLEMENTED** (CTO review pending)

## 1. Objective

Demonstrate that FakeMarket can generate real trading activity, lose authority under
a realistic failure, fence the old writer, promote a new authority using **existing**
P9 mechanisms, verify P8.6, resume trading with WAL continuity, and keep exactly one
authoritative financial writer.

This is a **production demonstration**, not a new reliability subsystem.

## 2. Architecture

```
P10.3 command stream (seeded)
        ↓
TradingService.WithAuthority(gate)
        ↓
AuthorityGate (P9.5 Node | P9.6 consensus.Node)
        ↓
Router / Workers → Risk → Match → Financial WAL
        ↓
LivePublisher → MD Hub (P10.3)
        ↓
P8.6 VerifyStateWithBaseline (recovery oracle)
```

### Honest packaging boundary

| Layer | What it is |
|-------|------------|
| Compose `node-a/b/c` | HTTP `/health` `/ready` `/metrics` packaging (P10.1) — **no trading/consensus** |
| `fakemarket-demo` | Real P9.6 FileTransport + P9.5 Promote + gated TradingService |
| Grafana/Prometheus | Can scrape demo `-metrics-addr` when configured |

**Do not claim:** killing Compose `node-a` fails over financial authority. That packaging
path does not run the trading stack.

## 5. Failure scenarios

### F1 — Canonical: primary authority loss via partition (P9.6)

1. FileTransport elects **A**
2. TradingService gated by A; P10.3 stream traffic; MD live publisher
3. Pre-failure P8.6 PASS + checkpoint
4. **Inject:** partition A\|BC + A `StepDown`
5. Stale A Submit → **rejected**, WAL/cash unchanged
6. Majority BC elects **B**; shared `authority.json` term advances
7. Mid P8.6 PASS (recovered prefix)
8. Re-gate service to B; resume traffic; Event.Sequence advances
9. Post P8.6 PASS
10. Heal partition; A remains non-authoritative; writers = 1
11. Stale A still rejected; B still accepts

**Why real:** FileTransport RPC, SharedAuthority fence, structural Service gate.

### F3 — Real OS process kill (canonical production failure)

1. Parent spawns **child OS process** holding solo leader A + TradingService + WAL + MD  
2. Child runs P10.3 traffic, writes checkpoint, stays alive  
3. Parent **`SIGKILL`s the child PID** (not `StepDown`, not `DetectFailure`)  
4. Parent confirms process exit (`Wait`, `kill(0)` → ESRCH)  
5. **Full `VerifyStateWithBaseline` P8.6** on recovered WAL (post-crash)  
6. `SharedAuthority.CommitLeader(B)` — cross-process fence SoT  
7. `trading.BootstrapResume` (StartupRecover + OpenResumed) — Event.Sequence continues  
8. Stale A gate rejects; B accepts; post traffic; sequence advances  
9. Restarted A cannot authorize; B still accepts  

**Detection:** process death (OS) + SharedAuthority reload on AuthorizeCommand.  
**WAL source:** same on-disk WAL directory recovered by survivor.  
**Old process after restart:** SharedAuthority says B → Authorize fails; cannot append as authority.

### F2 — Secondary: primary failure → replica promote (P9.5)

1. Bootstrap primary **node-A** with gated Service
2. Traffic + replica **CatchUpFromWAL**
3. **Inject:** `DetectFailure(node-A)` + `SetReady(false)`
4. `failover.Promote` (eligibility → fence old → recover replica WAL → OpenResumed)
5. Stale A Submit → **ErrAuthorityRejected**, zero mutation
6. Re-gate to node-B; resume; WAL advances
7. P8.6 PASS before/after; second recovery stable

**Why selected:** Different stack from F1 (in-process ClusterAuthority + replication
CatchUp + Promote fence-before-write), proving P9.5 path independently of consensus partition.

## 6. Failure injection

| Scenario | Injection | Not used |
|----------|-----------|----------|
| F1 | `FileTransport.SetPartition` + `StepDown` | Mocked Fail(), manual WAL edit |
| F2 | `DetectFailure` + ready clear + Promote | Manual token forge |
| F3 | **OS `SIGKILL` of primary child PID** | Mocked Fail(), in-process StepDown only |

Compose process kill of HTTP shells is **out of financial path** (documented limitation).  
F3 is the genuine process-boundary failure for financial authority+WAL.

## 7. Authority transition

F1: A term T → B term T+1 via quorum election + `CommitLeader`  
F2: epoch E → E+1 via `BeginPromote` fence-then-install  

## 8. WAL recovery & continuity

- Pre-failure: recover WAL → P8.6  
- Post-promote (no new cmds): same Event.Sequence / Trade.Sequence  
- Post-resume: Event.Sequence **>** pre-failure  
- Second `RecoverDir` identical prefix (idempotent)

## 9. Financial verification

Reuses `recovery.RecoverDir` + `invariants.VerifyStateWithBaseline` only.  
No P10.4-specific invariant engine.

## 10. Stale authority

Stale Submit/Cancel through Service with old gate:

```text
authority rejected
WAL sequence unchanged
cash/positions unchanged
```

## 11. Healing

F1 heal: A does not regain AuthorizeCommand; writers == 1  
F2: fenced A remains rejected after B resume  

## 12. Market Data

LivePublisher attached; MD events advance pre- and post-failure.  
No WS client required (metrics via Hub.Publish).

## 16. Limitations

1. Compose HTTP nodes ≠ consensus participants  
2. F1 financial WAL is single-process (authority moves; not multi-master log)  
3. F2 follows P9.5 in-process promote pattern (same trading stack, gate swap)  
4. F3 after resume: live matcher books start empty (sequence continuous; resting book is recovery oracle). Post-resume P8.6 uses conservation + dual recovery; full structural `book.no_cross` on cold-resume+new-traffic is deferred until hot book rebuild.  
5. No unsafe client retry  
6. P7 owns formal benchmarks  

## 17. Deferred

- Wire trading+consensus into `cmd/fakemarket` Compose nodes (packaging extension)  
- TCP gRPC multi-container Raft  
- Full multi-master financial log replication beyond P9.4 shipping

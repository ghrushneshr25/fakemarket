# P9.5 — Failover

## Status

🟢 **ACCEPTED / CLOSED** — commits `5b58281` + `04831af` + `7920694`.

## Goal

When Primary is unavailable, promote an eligible Replica to sole authority and continue
WAL history — without dual writers.

## Authority model

```
AuthorityToken { Node, Epoch, Generation, WALSeq }
ClusterAuthority.Validate(token)  // fence gate
Node.AuthorizeCommand()           // ready + role + Validate
```

## State machine

```
PRIMARY ──DetectFailure──► FAILURE_DETECTED
REPLICA ──eligible──► PROMOTING ──success──► PRIMARY
OLD PRIMARY ──BeginPromote fence──► FENCED
```

## Promotion order (critical)

1. Eligibility (healthy, durable==applied, P8.6, WAL integrity)
2. **Fence old token**
3. Install new epoch/owner
4. Recover replica WAL / verify state
5. `OpenResumed` writer at LastApplied
6. SetReady → accept commands

## WAL continuity

`next Event.Sequence = LastApplied + 1` — no reset, no rewrite.

## Failure detector

`DetectFailure` = **suspected** unavailability, not global death proof.
Does not promote alone.

## Structural authority gate (A2)

`TradingService.WithAuthority(gate)` binds a failover `AuthorityGate`.

Every **Submit** and **Cancel** calls `checkAuthority()` **before** router/executor/WAL.

```
Client → Service → Ready → AuthorityGate.AuthorizeCommand() → Router → … → WAL
```

Callers cannot bypass the fence by forgetting a helper API: the service path enforces it.

Nil gate = legacy single-node (no failover). Failover-enabled nodes **must** set the gate.

## Fencing domain — Option A (explicit)

**P9.5 fencing SoT is the shared in-process `ClusterAuthority`.**

Guarantees:

- Within one authority domain (shared registry), stale tokens cannot pass `TradingService` Submit/Cancel.
- Dual-writer is prevented when both “nodes” consult the same `ClusterAuthority`.

**Does NOT claim:**

- Cross-process fencing when Process A and Process B have independent memory.
- Automatic invalidation of an isolated old process that never observes the new epoch.

That cross-process agreement is **P9.6**.

## P9.5 vs P9.6

| P9.5 | P9.6 |
|------|------|
| Fencing within shared authority domain | Formal consensus / split-brain |
| In-process ClusterAuthority + Service gate | Multi-process agreement |

## Red lines

No dual writers; no boolean-only fence; no sequence reset; no promote from corrupt state;
no claim “split-brain solved.”

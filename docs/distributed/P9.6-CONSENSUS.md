# P9.6 — Consensus / Split-Brain Prevention

## Status

**IMPLEMENTED** (Raft-style quorum authority). Formal CTO 🟢 ACCEPTED pending review.

## Core question

> Can two partitioned nodes both pass the authoritative command gate and mutate financial state?

**Required answer: NO.**

## Model

```
Consensus Group {A,B,C}
        quorum = 2
             │
    exactly one LEADER (or zero if no quorum)
             │
             ▼
    TradingService.AuthorityGate (consensus.Node)
             │
             ▼
    Financial WAL (Event.Sequence)
```

## Roles

`FOLLOWER` → (timeout) → `CANDIDATE` → (quorum votes) → `LEADER`

## Quorum

`floor(N/2)+1` — minority partition cannot elect.

## Durable state

`DataDir/<node>/consensus-meta.json`: `currentTerm`, `votedFor` (fsync).

## Authority gate

`Node.AuthorizeCommand()` succeeds **only** if `IsLeader()`.

Wired via existing P9.5 `TradingService.WithAuthority`.

## Safety vs liveness

| | |
|--|--|
| **Safety** | Never two authoritative writers |
| **Liveness** | Elect leader when quorum reachable |
| Total partition | Zero leaders OK |

## Partition tests

- 3-node elect one
- Isolate leader; majority elects; heal → one writer
- Total partition → zero writers
- Stale leader Submit via real TradingService → reject, zero mutation

## Two layers (explicit)

| Layer | Role | Mechanism |
|-------|------|-----------|
| **Consensus election** | WHO wins leadership via quorum votes | RequestVote RPC (in-mem or **FileTransport**) |
| **SharedAuthority fencing** | Cross-process gate after election | `authority.json` fsync; AuthorizeCommand reloads |

`authority.json` is **not** the election. It is the **committed-authority fencing artifact** written only after a node obtains quorum votes.

## File-based quorum election (A|BC)

`TestP96_FileTransport_Partition_BC_Elects`:

1. A elected via file RPC votes  
2. Partition A|BC (blocked edges)  
3. **B ForceElection → C grants RequestVote over files → B CommitLeader**  
4. A Service.Submit rejected; B Submit advances WAL  
5. Heal → A still non-authoritative; exactly one writer  

## Authority linearization

```
quorum votes → becomeLeader → CommitLeader fsync → AuthorizeCommand may pass
```

## Authoritative financial prefix

| Name | Meaning |
|------|---------|
| `LocalDurableSeq` | Local WAL LastSequence (may include unreplicated suffix) |
| `LastLogIndex` (election) | **Must** equal durable/**replicated** prefix only |
| `AuthoritativeFinancialSeq` | Written into authority.json at leadership commit |

**Unreplicated suffix** on an isolated leader is **not authoritative** and must not be advertised as LastLogIndex. After heal, old leader must not append that suffix under a stale term (gate rejects).

## AuthorityGeneration (not Raft CommitIndex)

`AuthorityGeneration` = monotonic authority-install counter.  
**Not** a Raft log commit index. Full Raft financial-log commit is out of scope; financial replication remains P9.4.

## Explicit non-goals

Full Raft financial log replication, BFT, K8s, external DB, P10.

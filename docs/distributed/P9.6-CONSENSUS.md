# P9.6 — Consensus / Split-Brain Prevention

## Status

**IMPLEMENTED** (Raft-style quorum authority). Formal CTO 🟢 ACCEPTED pending review.

## Core question

> Can two partitioned nodes both pass the authoritative command gate and mutate financial state?

**Required answer: NO.**

## Model

```
Consensus Group {A,B,C}
        quorum = 2
             │
    exactly one LEADER (or zero if no quorum)
             │
             ▼
    TradingService.AuthorityGate (consensus.Node)
             │
             ▼
    Financial WAL (Event.Sequence)
```

## Roles

`FOLLOWER` → (timeout) → `CANDIDATE` → (quorum votes) → `LEADER`

## Quorum

`floor(N/2)+1` — minority partition cannot elect.

## Durable state

`DataDir/<node>/consensus-meta.json`: `currentTerm`, `votedFor` (fsync).

## Authority gate

`Node.AuthorizeCommand()` succeeds **only** if `IsLeader()`.

Wired via existing P9.5 `TradingService.WithAuthority`.

## Safety vs liveness

| | |
|--|--|
| **Safety** | Never two authoritative writers |
| **Liveness** | Elect leader when quorum reachable |
| Total partition | Zero leaders OK |

## Partition tests

- 3-node elect one
- Isolate leader; majority elects; heal → one writer
- Total partition → zero writers
- Stale leader Submit via real TradingService → reject, zero mutation

## Cross-process fencing

`SharedAuthority` (`authority.json`) is the disk-backed committed leader SoT.

Linearization of financial authority:

```
election quorum → CommitLeader(term, id, financialSeq) fsync
                → AuthorizeCommand reloads disk
                → must match committed LeaderID+Term
```

An isolated OS process that still believes it is Leader **reloads shared authority**
on every AuthorizeCommand and is fenced when another process committed a higher term.

**Test:** `TestP96_CrossProcess_SharedAuthority_FencesOldLeader` (child process commits B).

## Commit / applied semantics

| Index | Meaning |
|-------|---------|
| `CommitIndex` | Authority install count (consensus meta) |
| `FinancialSeq` | Leader's durable Event.Sequence at authority commit |
| `LastLogIndex` | Advertised financial prefix for election safety |

Authority is effective only **after** durable CommitLeader (when SharedAuth configured).

## Log freshness

Voters reject candidates with `LastLogIndex < voter.LastLogIndex`.

**Contract:** `LastLogIndex` must be the **durable/replicated** financial prefix only —
unreplicated leader-only suffix is not authoritative (P9.4 durable-before-ack).

## Explicit non-goals

Full Raft financial log replication, BFT, K8s, external DB, P10.
